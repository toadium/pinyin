## 发现

- **[一般]** 实际 `moon check` 警告类型与设计预期不符，且处置策略不完整。设计 §E 验证契约声称"可能含零源文件相关警告"，错误处理失败模式表第 4 行预期警告为"缺少源文件"。但经实测（moon 0.1.20260713，复刻设计的空骨架结构），实际产生的警告是 `Warning (0029) (unused_package): Unused package 'pinyin/pinyin/data'`，根因是主包无源文件导致 import 的数据子包未被引用，而非"缺少源文件"。设计未覆盖此实际警告类型，未给出根因分析，未说明该警告在后续任务添加引用 `@data.xxx` 的源文件后会自动消失。用户偏好明确要求"不忽略任何警告"（requirement.md:39），设计须对每个可预见的警告给出明确根因与处置。

- **[一般]** 设计未对 `moon check` 的警告提出与用户偏好一致的治理策略。requirement.md:39 与 task_v1.md 上下文均强调"偏好彻底的根因分析，不忽略任何警告"。设计 §E 后置条件仅写"可能含零源文件相关警告（若存在，记录但不阻断）"，"记录但不阻断"既未明确记录到何处、以何种形式记录，也未说明"不阻断"的判定依据。对于本任务唯一可预见的 `unused_package` 警告，应明确：该警告为空骨架阶段的预期产物，根因为主包尚无源文件引用数据子包，处置为接受并在后续任务（添加 `pinyin_helper.mbt` 等使用 `@data.xxx` 的源文件）后自然消除；若后续任务完成后警告仍存在则视为缺陷。

- **[轻微]** 设计 §C 与技术方案 §3.3 的 `data/moon.pkg` 注释文本存在细微差异（设计增加"（后续任务填充）"括注）。语义一致，不影响 `moon check`，但设计声明"精确到字节"与技术方案"精确到字节"两处口径下注释文本不统一，建议对齐以避免编码 agent 困惑。

## 修改要求（仅 REJECTED 时）

### 问题 1：实际警告类型与预期不符

**问题是什么**：设计预期 `moon check` 可能产生"缺少源文件"警告，但实测产生的是 `unused_package` 警告。设计未覆盖实际警告类型。

**为什么是问题**：用户偏好"不忽略任何警告"（requirement.md:39），设计须对每个可预见警告给出根因与处置。预期警告类型错误会导致编码 agent 在遇到 `unused_package` 警告时无法对照设计判断其是否预期，可能误判为缺陷并添加不必要的占位源文件，或误忽略真实缺陷。

**期望的修正方向**：
1. 在 §E 验证契约的"预期输出"中，将"可能含零源文件相关警告"替换为明确声明：预期产生 `Warning (unused_package): Unused package 'pinyin/pinyin/data'`，exit code 0。
2. 在错误处理失败模式表中，将第 4 行"缺少源文件"替换或补充为 `unused_package` 警告条目，根因为"主包无源文件，import 的数据子包未被引用"，处置为"预期警告，接受；后续任务添加引用 `@data.xxx` 的源文件后自动消除"。
3. 移除或修正 §C 中关于"moon 工具链要求包至少有一个 `.mbt` 文件"的预期——实测表明 moon 0.1.20260713 不要求空包有源文件，该预期不准确。

### 问题 2：警告治理策略不完整

**问题是什么**：设计对 `unused_package` 警告的处置仅写"记录但不阻断"，未明确记录位置、形式与不阻断的依据。

**为什么是问题**：用户偏好"彻底的根因分析，不忽略任何警告"要求每个警告都有明确的根因分析与处置决策链。"记录但不阻断"过于模糊，无法指导编码 agent 产出可追溯的验证记录。

**期望的修正方向**：在 §E 后置条件中补充警告治理子项，明确：(a) 警告类型与消息文本；(b) 根因（主包零源文件 → import 未被引用）；(c) 处置决策（接受为预期，不阻断本任务验收）；(d) 消除条件（后续任务添加使用 `@data.xxx` 的源文件后警告消失）；(e) 记录方式（在编码产出说明中记录警告原文与处置决策）。
