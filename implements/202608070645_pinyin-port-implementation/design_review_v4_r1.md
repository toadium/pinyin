## 发现

### 1. **[严重]** `dedup_by_key` 等价实现建议 `dict(reversed(items))` 保留首次 value，与核心目标"保留末次 value"矛盾

设计 §类型定义/去重逻辑规格（第 166 行）写道：

> **实现方式**：从右到左遍历（或反向遍历），首次遇到的 key 即原列表末次出现的 key，保留；后续遇到的相同 key 丢弃。**或等价地**：用 `dict` 倒序覆盖（`dict(reversed(items))`），再转回列表。

这两种方式**不等价**。以 `items = [('a',1), ('b',2), ('a',3)]` 为例（已用 Python 实际执行验证）：

| 方式 | 结果 | 保留的 value |
|------|------|-------------|
| 从右到左遍历，首次保留 | `[('a',3), ('b',2)]` | 末次（a:3）✓ |
| `dict(reversed(items))` | `{'a':1, 'b':2}` | **首次**（a:1）✗ |
| `dict(items)`（正向构造） | `{'a':3, 'b':2}` | 末次（a:3）✓ |

**根因**：`dict()` 构造时按迭代顺序插入，**后出现的 key 覆盖先出现的**。`dict(reversed(items))` 以反向序列构造，原列表中**首次**出现的 key 在 reversed 序列中**最后**出现，因此覆盖了末次 value，最终保留的是首次 value——与设计核心目标"保留末次 value（与 MoonBit Map 字面量及源库 Cangjie HashMap 语义一致）"**完全相反**。

**危害**：
- 若编码 agent 采信"或等价地"建议直接实现 `dict(reversed(items))`，去重将保留**首次** value 而非末次。
- 条目数断言仍会通过（去重后条目数相同，2533/843 不变）。
- `maps_*` 测试用例可能仍通过（取决于重复 key 是否落在测试覆盖的映射中）。
- `moon test` 可能 26 tests 全通过，但**实际数据与源库语义不一致**（保留首次而非末次），构成**测试无法捕获的隐藏语义保真缺陷**。
- 直接违背设计自身 §去重语义保真论证 的结论。

**正确的 `dict` 等价实现**应为 `dict(items)`（正向构造，后者覆盖前者 = 保留末次），而非 `dict(reversed(items))`。

### 2. **[一般]** 审计日志规格自相矛盾：声称用 `repr()` 形式，又要求"对 Int 显示十进制+十六进制"

设计 §去重逻辑规格（第 171 行）：

> `{key_repr}` / `{kept_repr}` / `{dropped_repr}`：key 与 value 的 `repr()` 形式（便于追溯，**对 Int 显示十进制+十六进制**，对 String 显示原始字符）

Python `repr()` 对 `int` 只返回十进制字符串（如 `repr(33266)` → `'33266'`），**不返回十六进制**。要同时显示十进制和十六进制需自定义格式化（如 `f"{v} (0x{v:X})"`），而非 `repr()`。

规格同时声明"用 `repr()` 形式"和"对 Int 显示十进制+十六进制"，二者不可兼得，编码 agent 无法确定应遵循哪个要求。审计日志是去重决策可追溯性的关键输出，规格歧义可能导致实现偏差。

### 3. **[轻微]** 测试文件文档注释更新保留旧行号，去重后实际行号已变

设计 §行为契约/F（第 420、426 行）：

> `chinese_dict_test.mbt` 文档注释同步：`条目第 13-2555 行共 2543 条` → `条目第 13-2555 行共 2543 条，去重后 2533 条`

### 4. **[轻微]** `dedup_by_key` 签名使用未定义的泛型类型变量 `K`、`V`

设计 §函数签名（第 118 行）：


`K` 和 `V` 在签名中用作泛型类型变量，但设计未声明 `TypeVar`（如 `K = TypeVar('K')`）。作为规格伪代码可接受，但实际实现需补充 `from typing import TypeVar` 声明或改用 `list[tuple[Any, Any]]`。

### 5. **[轻微]** 文件行数分类与示例不一致（总数正确）

设计 §行为契约/D（第 366 行）：

> 文件总行数：2（文档注释）+ 1（去重说明注释）+ 1（声明）+ 2533（条目）+ 1（收尾）= 2538 行

但 §类型定义/chinese_dict 示例（第 205-208 行）展示 3 行 `///` 文档注释（含去重说明行），非"2 行文档 + 1 行去重说明"。数学总和 2538 正确，但分类拆分与示例展示形式不一致，可能造成行数计算的误解。

## 修改要求（仅 REJECTED 时）

### 针对发现 1（严重）

**问题**：设计声称"从右到左遍历首次保留"等价于"`dict(reversed(items))`"，但后者保留首次 value 而非末次，与核心目标矛盾。

**为什么是问题**：编码 agent 若采信等价建议直接实现 `dict(reversed(items))`，将产生与源库语义相反的去重结果，且测试无法捕获此缺陷（条目数不变、映射测试可能不覆盖重复 key），导致隐藏的语义保真缺陷。

**期望修正方向**：
- 删除"或等价地：用 `dict` 倒序覆盖（`dict(reversed(items))`），再转回列表"这一错误建议。
- 若需保留 `dict` 等价实现，改为"或等价地：用 `dict` 正向构造（`dict(items)`），再转回列表（`dict` 构造时后出现的 key 覆盖先出现的，故保留末次 value）"。
- 保留"从右到左遍历，首次遇到的 key 保留"的正确描述不变。

### 针对发现 2（一般）

**问题**：审计日志规格同时要求"用 `repr()` 形式"和"对 Int 显示十进制+十六进制"，二者矛盾。

**为什么是问题**：Python `repr()` 对 int 不返回十六进制，编码 agent 无法确定应遵循哪个要求，规格歧义可能导致实现偏差。

**期望修正方向**：明确二选一：
- 方案 A：审计日志统一用 `repr()`，删除"对 Int 显示十进制+十六进制"要求（`repr(33266)` → `'33266'`，`repr('臺')` → `"'臺'"`）。
- 方案 B：自定义格式化函数替代 `repr()`，如 Int 用 `f"{v} (0x{v:X})"`、String 用 `repr()`，并明确说明"非 `repr()` 形式，而是自定义格式化"。
