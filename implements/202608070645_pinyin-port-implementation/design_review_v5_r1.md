# 设计审查报告（v5 r1）

## 审查结果
REJECTED

## 发现

### 1. [严重] `pub(self) let` 语法不合法，设计核心语法无法编译

设计中四个常量均使用 `pub(self) let` 语法（detail_v5.md:46/61/76/91/152/155/158/161）。经实际编译验证（在项目根目录创建 `pinyin_dicts.mbt` 按 design 文件结构写入后执行 `moon check`），MoonBit 编译器报 4 个 `Error [3005]: No 'public self' visibility for value`。

MoonBit 顶层 `let` 常量绑定**不存在 `pub(self)` 可见性修饰符**。该语法仅适用于函数（`pub(self) fn`）、类型等结构，对 `let` value 绑定非法。设计中全部四个常量定义、文件结构示例（§A 文件内容契约）、命名映射表均基于此不存在的语法，直接导致 `moon check` 失败，设计无法按当前形式实现。

### 2. [严重] `let`（私有）不能跨文件引用，"包内可见"目标对顶层常量无法实现

设计 §"可见性决策"（detail_v5.md:98-103）声称：

> 不使用 `let`（私有）：`let` 默认私有，但主包内跨文件引用需 `pub(self)` 可见性（MoonBit 顶层 `let` 跨文件引用要求至少 `pub(self)`）

经实验验证：在 `pinyin_dicts.mbt` 中以 `let chinese_map` 定义，在另一文件 `pinyin_dicts_ref_test.mbt` 的 test 块中引用 `chinese_map`，编译器报 `Error [4021]: The value identifier chinese_map is unbound`。

MoonBit 顶层 `let` 常量的可见性仅有两档：
- `let` — **文件内私有**，同包其他文件不可引用
- `pub let` — **公开**，跨包可引用

**不存在"包内可见但不暴露给外部"的可见性选项**。设计目标"仅主包内部可访问，不暴露给外部消费者"（detail_v5.md:11/101/149）对顶层 `let` 常量在 MoonBit 语言中无法实现。

### 3. [严重] 可见性决策三分支全部失效

设计 §"可见性决策"（detail_v5.md:98-103）比较了三个选项并选择 `pub(self) let`：

| 选项 | 设计中评估 | 实际验证结果 |
|------|-----------|------------|
| `pub(self) let` | "仅主包内部可访问"（选中） | **Error [3005]**，语法不合法 |
| `pub let` | "避免将字典视图暴露为公共 API"（排除） | 编译通过（1 warning），但确实暴露公共 API |
| `let` | "跨文件引用需 `pub(self)`"（排除） | **Error [4021]**，不能跨文件引用 |

三个分支中，被选中的 `pub(self) let` 不存在；被排除的 `let` 确实不可跨文件引用（设计此点判断正确）；被排除的 `pub let` 是唯一能编译通过的方案。可见性决策整体基于错误前提，需重新论证。

### 4. [一般] 验证契约预期输出与任何可行方案的实际结果不符

设计 §E 验证契约（detail_v5.md:230-242）预期 `moon check` 后 **1 warning**（`text_segment_excceed`），0 errors，`unused_package` 警告消除。

经实验验证两种可行方案的实际情况：

| 方案 | `moon check` 结果 | 是否符合预期 |
|------|------------------|------------|
| `pub let` | 1 warning（`text_segment_excceed`），0 errors | 警告数符合，但暴露公共 API（违反 §设计目标 3） |
| `let` | 5 warnings（4×`unused_value` + 1×`text_segment_excceed`），0 errors | 警告数不符（预期 1，实际 5） |

无论采用哪种修正方向，验证契约的预期输出均需更新。若采用 `let` 方案，还需处理 4 个 `unused_value` 警告（与本任务"不忽略任何警告"的用户偏好冲突，且这些警告要到 R5/R6/R7 引用后才会消除）。

### 5. [一般] 与任务指令 task_v5.md 的语法不一致

task_v5.md:10-26 的代码示例**未使用 `///|` 标记**，而 detail_v5.md:146 的文件结构**使用了 `///|` 标记**。经实验验证，`///|` 用法本身合法（编译通过），但两份文档对同一文件结构的描述不一致，实现者可能产生混淆。应统一为一种写法并说明理由。

注：`///|` 用法经实验验证合法（`pub let` 版本带 `///|` 编译通过，0 errors），此项仅为文档一致性问题。

## 修改要求

### 针对发现 1+2+3（核心语法问题）

**问题**：设计中四个 `pub(self) let` 常量定义使用不存在的 MoonBit 语法，且设计目标"包内可见不暴露"对顶层 `let` 常量在 MoonBit 中无法实现。

**为什么是问题**：按当前设计实现将直接产生 4 个编译错误（`Error [3005]`），`moon check` 无法通过，阻塞后续所有任务。设计的核心交付物（四个视图常量定义）基于不存在的语法。

**期望的修正方向**：在以下三种方案中选择一种，并全面更新设计文档：

- **方案 A（`pub let`，推荐）**：将四个常量改为 `pub let`。接受字典视图作为公共 API 暴露（MoonBit 语言限制下无法避免）。需更新：可见性决策（重新论证为何接受 `pub let`）、文件结构、命名映射表（可见性列改为 `pub let`）、设计目标 3（"不暴露"改为"暴露为公共只读常量"）、§C 共享语义契约。此方案编译通过、警告数符合预期、后续任务可直接引用。

- **方案 B（`pub(self) fn` 函数封装）**：将四个常量改为 `pub(self) fn` 零参函数，如 `pub(self) fn chinese_map() -> Map[Int, Int] { @data.chinese_dict }`。保持包内可见。需更新：类型定义（从 `let` 改为 `fn`）、文件结构、命名映射表、§C 共享语义契约（每次调用返回同一引用）、后续任务接口（引用方式从 `chinese_map` 改为 `chinese_map()`）。需验证函数调用是否被编译器内联（性能考量）。

- **方案 C（取消视图层）**：不创建 `pinyin_dicts.mbt`，后续 R5/R6/R7 算法文件直接引用 `@data.chinese_dict` 等。`unused_package` 警告由算法文件引用消除。需大幅重构设计（文件规划、类型定义、行为契约、依赖关系等均需重写），且本任务的存在意义需重新论证。

### 针对发现 4（验证契约）

**问题**：验证契约预期 1 warning，但可行方案的实际结果不同。

**为什么是问题**：验证契约是实现后判断任务是否完成的依据，预期与实际不符会导致验证阶段误判。

**期望的修正方向**：根据发现 1+2+3 选定的方案更新 §E 验证契约的预期输出。若选方案 A（`pub let`），预期 1 warning（`text_segment_excceed`），与当前预期一致，仅需删除对 `pub(self)` 的引用。若选方案 B，需验证 `pub(self) fn` 是否产生额外警告并更新预期。

### 针对发现 5（文档一致性）

**问题**：task_v5.md 与 detail_v5.md 对 `///|` 标记的描述不一致。

**为什么是问题**：实现者可能困惑是否需要 `///|` 标记。

**期望的修正方向**：在 detail_v5.md 中统一文件结构描述，明确是否使用 `///|` 并说明理由（如：用于标记顶层结构 text segment，符合 MoonBit 文档注释规范）。与 task_v5.md 保持一致（或说明 detail_v5.md 比 task_v5.md 更精确的理由）。
